# 実装契約と技術計画

仕様書と2026-10-20の追加合意に従い、Windowsを優先しWSLを独立した実行環境として検証する。

## 責務

- Python 3.13.17、PyTorch、Transformers: 実モデル推論、取得、数値検証。
- FastAPI: loopback API、セッション認証、ジョブ、ストレージ制御。
- React/TypeScript/Three.js: 全トークンの3D軌跡、タイムライン、Inspector。
- SQLite: 設定、モデル/Lens登録、ジョブとトレースの検索、研究レポート。
- トレース: version付きmanifest、所有マーカー、SHA-256、観測点単位のNPYチャンク。

NPYを初期保存形式とする。各観測点を逐次同期書き込みし、GPU履歴と無制限RAMキューを持たない。
読取時はmmapで部分参照可能。Zarrへの依存を必須にせず、フォーマット移行はschema_versionで扱う。
Level 1はPCA確定までResidualを一時スプールし、正常完了時に生テンソルを破棄する。

## 検証順序

1. 決定論的な極小SwiGLU Transformerと独立NumPy参照計算。
2. Residual/Attention/MLP再構成、固定PCA、変位と指標、保存と削除。
3. API・失敗パス・ジョブ再接続、3D表示と実際のUI操作。
4. Qwen3-0.6BのWindows/WSL GPU検証、比較と生成。
5. 介入の対照・復元・因果的な先頭不変性、複数実験統計、t-SNEの再現性、Lens変換を検証。

段階完了は停止条件ではない。実測結果と未対応項目をmodel-support.mdおよび検証文書へ記録する。

## モデルと空間

極小Transformerはランダム固定重みの実計算を行うテストモデルであり、事前学習済みLLMとして表示しない。
Qwen3とGPT-2は構造別アダプターで扱う。未対応アーキテクチャや量子化モデルの登録を拒否する。
Residual、Q/K/V、MLP中間空間を識別し、Residual主軌跡にはResidualに戻した更新のみ表示する。
Qwen3のQ/KはQK NormとRoPEを区別し、GQAのQuery→KV Head対応を保存する。

## 制約

対応モデル、最大長、PCA性能、同時ジョブ性能は実測で確定する。初期の推論ジョブは直列実行する。
共有PCAは実験内で固定し、比較時は両トレースから共通基底を再計算する。
未知のバックエンドで内部値を取得可能と表示しない。介入実験は観察と明確に分ける。

## 起動と解析エンジン

トレース一覧の利用可否は、要求ごとに所有マーカー・manifest・全参照チャンクの存在を確認する。チャンクごとの親パス・所有マーカーの再読込は避け、参照パスをフォルダーごとにまとめてscandirする。欠落判定を時間キャッシュせず、削除・復元・リンクの変更を次の要求で検出する。テンソル値を実際に読む際のパス検証と、明示的なSHA-256検証は維持する。

FastAPIプロセスではTorch・Transformers・SciPy・scikit-learnをimportしない。モデル一覧は登録メタデータ、取得済みトレースの閲覧はNumPy・ストレージだけで応答する。最初の画面描画後に `POST /api/runtime/start` を呼び、spawnした常駐ワーカーで重いライブラリを読み込む。ブラウザーを使わない解析APIからも同じ準備を開始する。

準備状態は `GET /api/runtime` の `idle / starting / ready / failed` で共有する。同時要求・画面再読み込みではワーカーを増やさない。失敗時は明示的な再試行だけで再起動する。ワーカーの異常終了時は進行中ジョブを失敗へ遷移させ、閲覧用APIは継続する。準備済みの同じワーカーで解析・事前確認・モデル/Lens登録・共通PCA・研究を実行する。GPU/モデル処理は一つのexecutorで直列化し、制御用受信ループは中止要求を受け付け続ける。

解析受付時に `loading_runtime` ジョブを保存する。`created_at` から終了までの `elapsed_seconds` は準備待ち・実行待ちを含む。待機中の解析を中止しても、他の操作と共有する準備は中止しない。非解析操作は呼び出したパネルにローダーを表示し、架空の進捗率を出さない。ワーカーがカタログへ接続する際は `Store(..., recover=False)` を使い、メインプロセスの生きたジョブを起動時回復処理で失敗にしない。設定・保持先変更は各呼び出し時にワーカーへ反映する。

解析開始時のTokenizer・容量・デバイス検証はジョブ内の最初の工程で行う。入力スキーマなどの軽い検証を通れば202で受付し、実行前チェックで不適合ならジョブを失敗として表示する。開始前に確認したい場合は従来の「トークン・容量を確認」を利用できる。

Helix Threadは添付のSTATE OF PLAY v4.8.0をテーマに合わせて組み込み、二本の鎖の位相と形状を保つ。画面外・非表示タブ・`prefers-reduced-motion` では動きを止め、状態文は `role=status` で伝える。

## モデルの検出・登録

検出はGPUジョブと独立した有界の単一スレッドで行い、設定とファイル存在のみを確認する。登録時にTokenizerの読込、safetensorsヘッダー、全ファイルのfingerprintを検証する。登録・追加探索先はSQLite、解析画面で最後に選んだモデルIDはブラウザへ保存する。
登録済みの必要ファイルが失われた場合は利用不可を返し、保存場所の更新はfingerprint一致を条件に元の登録IDを維持する。フォルダー選択はバックエンドOSの1階層を取得するWebダイアログであり、Windows／WSLで同じUIを用いる。API・探索上限・検証範囲は[ローカルモデルの登録](model-registration.md)を参照。

## 研究処理

研究処理も同じ直列executorを使う。介入なし・介入あり・介入解除後を同じモデルインスタンスで計算し、Hookをfinallyで必ず解除する。取得済み元トレースには書き込まない。使用する保存値のSHA-256を確認し、研究処理中の参照元は削除・保持先への移動・自動整理から除外する。

確定したレポートはSQLiteのstudiesへ原子的に保存する。ブラウザの状態から切り離し、終了していない研究ジョブは再起動時に失敗へ遷移する。JSONは実行条件と結果、CSVは結果表を提供する。元トレースのZIPとは独立した形式である。
